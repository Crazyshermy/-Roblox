**Headless mode** (Linux or cloud session, CI): no Studio, so `studio` is unavailable and the companion plugin is absent. The daemon serves the brain from files and the mirror `.rbxl`. Tests run through Lune (pure logic) and Open Cloud Luau Execution (engine). Visual, input, and multiplayer evidence is marked *unavailable*, never faked.

### A.3 Planes and trust boundaries

| Plane | Contents | Trust |
|---|---|---|
| **Control plane** | Hooks, policy engine, permission tiers, confirmations | Trusted (our code) |
| **Data plane** | Index, snapshots, telemetry, screenshots, analytics | Trusted storage, **untrusted content** (game text, asset metadata, logs) |
| **Action plane** | Studio edits, Luau execution, publishing, config changes | Gated by policy. Every mutation is journaled. |
| **External** | Open Cloud, docs, toolbox assets | Least-privilege credentials, provenance tagging |

Boundary rules:
- (1) Content from the data plane never upgrades permissions.
- (2) Production credentials are never available to Studio-side code.
- (3) The daemon binds only to loopback and authenticates every client: hooks and MCP use a socket with file permissions, and the Studio plugin uses an embedded per-install token.

### A.4 Core runtime loop

Every `/roblox` task runs the same macro loop. Claude can enter it at any stage.

```
  INTENT ─► CONTEXT ─► REALITY CHECK ─► PLAN ─► CHECKPOINT ─► IMPLEMENT
     ▲                                                          │
     │                                                          ▼
  REPORT ◄─ DECIDE(keep/revert/iterate/stop) ◄─ EVALUATE ◄─ VERIFY (static→unit→
     │         ▲                                   │          scenario→MP→visual→perf)
     │         └── diminishing-returns detector ◄──┘ critic / player evidence
     └─► MEMORY UPDATE (decisions, lessons, experiments, brain deltas)
```

What follows is a card per component: why it exists, what problem it solves, whether it is essential, whether it can be deferred, its cost, and what it enables.

### B1. `rbxos` binary and `rbxosd` daemon
- **Why:** MCP stdio servers live and die with a Claude session. Indexes, watchers, Studio connections, and long jobs (multiplayer suites, bot populations, snapshot uploads) must persist across sessions, be shared by the main session and subagents, and survive Claude crashes.
- **Solves:** state continuity, concurrency control (a single writer per project), crash isolation, and fast hooks.
- **Design:**
  - A single Rust binary with subcommands: `daemon`, `mcp`, `studio-gateway`, `hook`, `watch`, `context`, `doctor`, `install`, `ci`, plus admin commands.
  - The daemon is started on demand: the first client spawns it, a lockfile guards it, and it exits after idling for 30 minutes.
  - Clients talk to it over an authenticated local socket (Unix domain socket or Windows named pipe) using JSON-RPC 2.0.
  - Services inside the daemon are actors (tokio tasks) with a per-project write lock.
- **Essential:** yes. **Defer:** no. **Cost:** M build.

### B2. Studio MCP Gateway
- **Why:** Using the built-in server directly gives no policy, no journaling, the risk of targeting the wrong Studio, and occasionally huge outputs.
- **Design:**
  - A transparent stdio JSON-RPC proxy to the platform's `StudioMCP` executable.
  - It intercepts only `tools/call` for known tool names:
    - `studio_id` pinning: injects the project's Studio when the call omits it, and rejects mismatches.
    - Pre-mutation checkpoint for `multi_edit`, `execute_luau` (Edit DM), `insert_asset`, and generation tools.
    - Journaling of input and output digests.
    - **Output shaping:** `search_game_tree` and `script_grep` results are summarized and given handles once they pass a size threshold, and the full result is stored in the daemon for `rbxos.expand`.
  - Unknown tools pass through and are classified `ask` by default until a policy entry exists.
  - `list_changed` is forwarded.
  - If the gateway fails to start, `doctor` offers a direct configuration.
- **Essential:** yes. Without it, the built-in tools bypass versioning. **Cost:** S.

### B3. Policy Engine
- **Why:** The system has significant power, including production publishing and data.
- **Design:**
  - Tiered capabilities (file 08 §L.1) are evaluated at four enforcement points: Claude Code `PreToolUse` hooks, the gateway, the daemon (for `rbxos` tools), and the companion plugin.
  - Static screening of Luau passed to `execute_luau` (full-moon AST: `Destroy` on service roots, `ClearAllChildren`, DataStore writes, `TeleportService`, Marketplace prompts, external `HttpService`) escalates the call to `ask`.
  - Protected paths are declared in the constitution.
- **Essential:** yes. **Cost:** M.

### B4. Claude Code plugin
- **Why:** This is how capabilities reach Claude without modifying Claude.
- **Contents:**
  - The `roblox` entry skill and about 10 mode skills.
  - Knowledge skills activated by `paths`.
  - About 12 specialist agents.
  - Hooks: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop`, `SubagentStop`, `PreCompact`/`PostCompact`, `SessionEnd`.
  - A monitor, the LSP, workflows, and `userConfig`.
- Details are in file 03.

### B5. Indexer and Project Brain
- **Why:** Claude should never rediscover the project.
- **Design:**
  - Layered graph store (file 06 §G): L1 index (instances, scripts, symbols, requires, remotes, tags, attributes, connections, assets), L2 semantic model (systems, responsibilities, data flows, client/server boundary, remote contracts), L3 intent (constitution, design), and a runtime overlay (traces).
  - Updates are incremental: file events, bridge `DescendantAdded/Removing` plus `ChangeHistoryService` events, and content hashes.
- **Essential:** yes. **Cost:** L.

### B6. Semantic Search
- **Why:** "Where is player death handled?"
- **Design:**
  - Hybrid retrieval: BM25 over code and comments, symbol lookup, a **concept lexicon** from the knowledge layer (for example, death → `Humanoid.Died`, `HumanoidStateType.Dead`, `Health <= 0`, `CharacterRemoving`, `LoadCharacter`), graph expansion, and runtime traces.
  - Returns an **architecture slice** (entities, edges, line ranges), not files.
  - Embeddings are optional (Phase 6+). Lexicon plus graph is expected to cover most queries in game code, where naming is idiomatic (⚠ measure in Phase 1 against a labeled query set).

### B7. Context Router
- **Why:** This is the main lever for usage efficiency and for relevance.
- **Design:** A deterministic pipeline in the daemon: classify, select, score, budget, pack, dedupe. Claude receives CRITICAL items inline and IMPORTANT and OPTIONAL items as handles. STALE items are suppressed and flagged. (File 06 §H.)

### B8. Memory
- **Why:** It prevents re-litigating decisions and repeating mistakes.
- **Design:** Plain files in `.rbxos/` (Markdown with YAML frontmatter), indexed by the daemon, and routed into context. Decisions carry *reopen conditions*.

### B9. Companion Studio Plugin and Bridge
- **Why:** Most deep capabilities are plugin-security APIs that the built-in server doesn't expose.
- **Design:** Luau (strict). One bridge connection per DataModel role: Edit, Server, and Client-N. It exposes a capability RPC set (file 04 §E), injects the test runtime (bots, taps, invariants) only into test DataModels, and shows a small status dock widget (connected, tier, current task, *Stop agent* button).
- **Essential:** yes for local mode.

### B10. Versioning
- **Why:** Safe experimentation and automatic recovery.
- **Design:** Changesets (agent-attributed operation groups) and checkpoints (git shadow ref plus DataModel snapshot manifest plus optional place version), with semantic DataModel diffs, rollback, and **automated bisection** across changesets when a regression is detected. (File 10.)

### B11. Runtime Observation
- **Why:** Debugging requires correlating code, events, errors, visuals, and behavior.
- **Design:**
  - The plugin streams logs (with source DM and stack), errors (deduplicated by signature), remote-traffic counters and samples, player state snapshots, custom game events (`AnalyticsService` calls are intercepted in tests), performance samples, and screenshots on trigger.
  - Everything lands in a columnar store (SQLite tables partitioned by test run), queried through `rbxos.runtime.query` with summaries.

### B12. QA Engine
- Static (luau-analyze strict, selene, StyLua, RBXOS rules) → unit (Jest-Lua via Lune or in-engine) → integration (Run mode) → scenario (DSL) → multiplayer (≤ 8 clients, staggered joins, leaves, latency) → chaos → fuzz → visual → performance. (File 08 §K.)

### B13. Quality Gates and Stop Governor
- Phase-dependent gate profiles: prototype, vertical slice, alpha, beta, live.
- The `Stop` hook evaluates the gates touched by the task's changesets. It may block once, with a reason, and must never loop.
- It also implements the **diminishing-returns detector** (file 08 §Q.3).

### B14. Architecture Guardian
- Deterministic metrics on every index update:
  - module size and responsibility count
  - fan-in and fan-out
  - cycles in the require graph
  - client/server boundary violations
  - duplicated code (token shingles)
  - dead modules (unreachable from entry points)
  - remote handlers without validation
  - unbounded connections (`Connect` without cleanup in per-player code)
  - growth rate per module
- Threshold crossings become findings, and an LLM review (`architect` agent) runs **only** for findings rated high.

### B15–B18. Performance, Visual, Device, Asset
See files 08 and 09. These are deterministic analyzers first. Vision and LLM judgment is applied only to their flagged output.

### B19. Security Adversary
- A malicious-client harness in client DataModels: a remote fuzzer, replay and spam, and argument mutation.
- **Invariants** (conservation of currency, inventory integrity) checked on the server DataModel.
- A static remote-validation analyzer, DataStore safety checks, and the free-model scanner.
- A `security-adversary` agent reasons about exploit chains.

### B20. Knowledge System
- Generated API facts, curated cards with claims and probes, a verifier, and a live-docs fallback. (File 05.)

### B21. Design Intelligence
- Skills and agents encode design reasoning (reality check, boundary breaker, scope options, creative risk, genre packs, game-feel model, anti-slop, critic).
- v1 (Phase 1) is reasoning-only. v2 (Phase 7) is backed by evidence from the simulation, feel instrumentation, and analytics.

### B22–B23. Player Simulation and Fun Laboratory
See file 07.

### B24. Live Ops and Analytics
- Open Cloud wrappers: publish to staging or production (gated), config drafts and publishes, experiments, analytics queries, and post-publish regression watching keyed by `PlaceVersion`.

### B25. Headless/CI mode
- `rbxos ci`:
  1. build (Rojo, or reconstruct the mirror)
  2. static gates
  3. Lune unit tests
  4. upload to a dev place
  5. Luau Execution test suites
  6. gate report (JUnit and Markdown)

### B26. Installer and Doctor
See file 11.

### What we deliberately do *not* build
- A custom LLM agent loop. Claude Code is the loop.
- A vector database service. SQLite plus optional `sqlite-vec` is enough.
- A web dashboard for v1. Claude Code plus Markdown reports plus the Studio dock widget are enough. A changeset viewer could later ship as an artifact-style HTML report.
- Our own A/B platform. We use Open Cloud Experiments.
- Our own file sync. We use Rojo or Script Sync.
- Our own asset generation models. We use the built-in generation tools, with pluggable external pipelines later.
