# 05: Knowledge Architecture (F)

## F.1 Goals and non-goals
**Goals:**
- Reduce hallucinated Roblox facts.
- Encode the *judgment* that documentation doesn't contain: when to use something, failure modes, tradeoffs.
- Make every important claim traceable and re-verifiable.
- Stay current as Roblox changes.

**Non-goals:**
- Mirroring the Roblox docs. Live lookup through the built-in `http_get` and the `rbx-docs-search` skill already exists.
- A universal "truth database". Knowledge is a set of *claims with evidence*.

## F.3 Card format

Cards are Markdown with YAML frontmatter, stored in a versioned knowledge pack. Here is an abbreviated example:

```markdown
---
id: k.engine.remote-event
kind: api-concept
title: RemoteEvent
concepts: [replication, client-server, security.remote-validation]
api: [RemoteEvent, RemoteEvent.OnServerEvent, RemoteEvent:FireServer, RemoteEvent:FireClient, RemoteEvent:FireAllClients, UnreliableRemoteEvent]
related: [k.pattern.remote-validation, k.pattern.rate-limiting, k.engine.remote-function, k.engine.unreliable-remote-event, k.engine.attributes-replication]
intents: [build, debug, security]
summary: >
  One-way, reliable, ordered message across the client/server boundary. The server must treat every
  OnServerEvent argument as attacker-controlled; the first argument is the sending Player (injected by engine).
claims:
  - id: c1
    text: "OnServerEvent's first parameter is the Player who fired; clients cannot spoof it."
    status: documented
    sources: [{type: docs, ref: "reference/engine/classes/RemoteEvent", version: "api@<hash>"}]
    probe: probes/remote-event/player-arg.luau
    last_verified: {status: pass, studio: "0.7xx", at: 2026-09-30}
  - id: c2
    text: "Instances passed as arguments arrive as nil on the receiver if they are not replicated to it."
    status: observed
    probe: probes/remote-event/nonreplicated-instance-arg.luau
  - id: c3
    text: "Tables with mixed keys / non-string keys lose data across the boundary."
    status: documented
  - id: c4
    text: "Prefer UnreliableRemoteEvent for high-frequency cosmetic state (≤ ~900 bytes payload)."
    status: documented
    note: "payload limit value must be re-checked against current docs"
when_to_use: [discrete player intents (Swing, Buy, Interact), server→client notifications]
when_not_to_use: [replicating continuous state → Attributes/ValueObjects or replicated properties, request/response with timeouts → RemoteFunction (and never server→client InvokeClient)]
security: [validate types/ranges/ownership/cooldowns server-side, rate-limit per player, never trust client-reported damage/currency/position deltas]
performance: [batch high-frequency events, prefer unreliable for cosmetic, avoid per-frame FireAllClients with large tables]
common_mistakes: [trusting args, firing before client listeners connect (startup race), creating remotes at runtime on client, one remote per item]
alternatives: [Attributes, ValueObjects, replicated properties, MessagingService (cross-server, not client)]
verification: {probes: 3, coverage: c1,c2}
---
## Details
… (loaded only on expand) …
## Examples
… minimal, idiomatic, strict-typed …
```

## F.4 Epistemic status and confidence (deterministic, no fake decimals)

| Status | Meaning | Confidence (derived) |
|---|---|---|
| `documented` | Stated by official docs or the API dump at a known version | High if the version matches the current Studio, otherwise Medium |
| `observed` | A probe passed on a recorded Studio version | High if the version matches and the result is ≤ 90 days old, otherwise Medium |
| `inferred` | Reasoned from documented facts or from code. No direct evidence. | Medium or Low |
| `convention` | Community practice (cited) | Not truth-apt. Presented as practice, with tradeoffs. |
| `uncertain` | Conflicting sources or untested | Low. Claude must verify before relying on it for critical decisions. |
| `outdated` | A probe failed, or the API is deprecated or removed in the current dump | Never presented as current. Shown with its replacement. |

**Derivation rules:**
- A card's confidence is the minimum over the claims the current task actually uses.
- Disagreement between `documented` and `observed` becomes `uncertain`, and a *discrepancy record* is filed (these are valuable: docs bugs or behavior changes).

## F.5 Verification pipeline

```
Studio version change detected (plugin hello / API dump hash)
      │
      ▼
API dump diff ──► K1 regenerated ──► affected members ──► claims referencing them → `needs_reverify`
      │                                                         │
      ▼                                                         ▼
Scheduled (nightly routine) / on-demand ──────────────► Probe runner
                                                       ├── Lune (pure Luau semantics)
                                                       ├── Sandbox Studio via execute_luau (Edit/Server/Client)
                                                       ├── Sandbox multiplayer (StudioTestService) for replication claims
                                                       └── Open Cloud Luau Execution (headless engine)
      │
      ▼
Evidence record {claim, probe, env, studio_version, result, output} → status transition
```

**Probe format.** A probe is Luau that returns a table: `{ok: boolean, observed: any, notes?: string}`. Its frontmatter declares `env: lune|edit|server|client|multiplayer|headless`, `timeout_s`, and any fixtures it requires. Probes run only in **sandbox places**, never the user's project.

**On-demand verification.** When the router supplies a claim with status `uncertain`, and the task is security- or data-critical, the pack marks it `VERIFY-BEFORE-RELYING`. Claude can call `rbxos.knowledge_probe(claim)`, which runs the probe in the sandbox in seconds.

**Discovery probes.** When Claude is unsure how the engine behaves (for example, "Does `Touched` fire for anchored-to-anchored parts?"), it can write an ad-hoc probe through `rbxos.knowledge_probe {code, env}`. The result is stored as a project-learned `observed` claim (K6) and can be promoted to the shared pack after review.

## F.6 Retrieval
- Indexed by concept id, API members referenced, intents, systems (via the Brain's API-usage links), and free text (FTS5).
- **The router selects cards from the task's API footprint.** The Brain knows which API members the touched modules use, so debugging `DamageService` automatically pulls the cards on `Humanoid` health, character lifecycle, and remote validation.
- **Progressive disclosure:** the `summary` (≤ 120 tokens) goes inline when CRITICAL. Claims and when-to-use sections come back on `expand`, and details and examples on a deep expand.

## F.7 Live fallback (no card exists)
1. `knowledge_lookup` queries K1 first, which always exists for API facts.
2. If the question is conceptual, it delegates to the built-in `http_get` (allow-listed Roblox docs) through the `researcher` agent (haiku-class). The answer comes back with citations.
3. The result is cached as an *ephemeral* `documented` or `inferred` claim with a 30-day TTL, and optionally queued as a **card draft** for review.

## F.8 Deterministic hallucination guards
1. **API existence check (PostToolUse):** every `Class.Member` or `Service:Method` reference in edited Luau is resolved against K1 using type information from luau-lsp. Unknown members, deprecated members, and wrong security contexts (for example, calling a PluginSecurity API from a game script, or a server-only API in a LocalScript, inferred from the script's run context) are reported immediately.
2. **Context check:** the Brain knows each script's execution context, so `DataStoreService` in client code, or `LocalPlayer` in server code, is flagged.
3. **Claim citation:** when Claude writes an ADR that depends on engine behavior, the `decision_record` tool asks for the knowledge claim ids it relies on. A decision that depends on an `uncertain` claim is recorded with `reopen_if: claim c… changes`.

## F.9 Authoring and governance
- Knowledge packs live in the RBXOS repo (`knowledge/`), are versioned with semver, and ship with plugin updates. Projects can override or add cards in `.rbxos/knowledge/`.
- **A pack CI gate requires a probe or a documentation citation for every engine-behavior claim.** Cards without one are refused as `documented` or `observed`.
- **Licensing:** API facts are generated from the API dump. Docs content is *paraphrased and linked*, not copied wholesale (⚠ confirm the creator-docs license terms before redistributing any verbatim text).
